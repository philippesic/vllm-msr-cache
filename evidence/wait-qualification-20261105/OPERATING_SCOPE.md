# Intended operating scope and selection rules

The intended use case is a single local server hosting overlapping, multi-turn
assistant workflows with exact growing prefixes, actual subprocess tool waits,
and CPU KV capacity under contention. The application can report an already
observed complete prefix and can refresh advice while a workflow is waiting.
The tested clients share a host monotonic clock with the server. This campaign
does not establish cross-host clock translation or production-agent traffic.

The original sixteen repository investigations are development evidence. The
independent evaluation families are sixteen more-itertools source/test tasks and
sixteen Python Enhancement Proposal analysis tasks. Their sixteen-task reserve
sets were frozen before candidate evaluation. Public source revisions and exact
executed files are retained with the runs. These authored pipelines represent
code inspection/testing and document search/parsing; they do not represent every
coding task, autonomous tool selection, or a weighted population of users.
No arithmetic average across the selected families estimates deployment-wide gain.

Before Stage 3, select the strongest equal-budget substitute from the Stage 2
systems and native LRU, excluding the candidate and the deliberately unequal
ARC-plus-memory diagnostic. Use geometric mean batch time across its complete
frozen repetitions, retain quality/activation limitations, and document the
choice. Compare every family against no-hint ARC and that substitute (deduplicate
if ARC itself is strongest). Include another rival if its documented capabilities
make the selected one unrepresentative of a new regime. Do not drop a strong
rival because a held-out result is unfavorable.

Start the independent families with the original byte budgets and scheduling.
Their actual context lengths may create less contention. Such an inactive or
neutral result is legitimate coverage, not a reason to pad contexts or discard
it. The separately predeclared constrained-cache and concurrency regimes expose
pressure using existing real inputs; their geometry must remain feasible for an
active request. Do not search capacities until a favorable number appears.
Ample-cache, mixed-traffic and serialized-tool regimes answer different questions
and remain separately reported. A single regime screen can diagnose behavior;
a public repeatability claim needs repeated complete batches.

For another model, convert GPU and CPU byte limits using its actual dense KV
geometry, round GPU blocks down, and disclose lost fractional-block capacity.
Context/concurrency must satisfy that model's supported limits. A combined change
needed for feasibility is a separate cell, not an isolated model effect. A
functional-only cell cannot support a performance claim.

The bounded churn exposure uses six sequential waves of sixteen real workflows
per condition, with independently staggered session admission inside each wave
(0.25 seconds between sessions), mixed hint assignment, and actual tools. Reusing
the tasks across waves is explicit; this is not an offered-load saturation test.
Require complete work, no request/tool failures, verified process cleanup, and
no more than 512 MiB growth in summed server RSS between the last five seconds
of the first and final waves. Report all wave endpoints; this permissive finite
bound cannot establish asymptotic bookkeeping behavior. The audited research
profile keeps generation history indefinitely, whereas the ordinary unaudited
profile bounds new session registration and eventually refuses new advice at
capacity. Neither behavior qualifies unlimited session churn without further
lifecycle work. This known limitation is not evidence against the retention
mechanism's measured usefulness within a bounded population.

Before either independent family is evaluated, also select one fixed combined
memory-constrained deployment cell for each: halve the original GPU and CPU byte
budgets (1,280 GPU blocks / 1,409,286,144 CPU bytes for the base model), leaving
other settings fixed. This represents memory reserved for other server consumers,
not a capacity search. The original full-budget result is retained, even if
neutral; report the combined cell separately. Use the same frozen held-out inputs
because both cells and the conversion rule were selected before any candidate
measurement. If input inspection shows the requested maximum context cannot fit
one GPU request, diagnose feasibility rather than silently truncate or tune until
it wins. The existing eight-sequence scheduler may admit fewer live sequences
under pressure; record real preemptions and completion for both conditions.

The observed upstream system remains an additional credible rival for independent,
constrained, concurrent and mixed cells even if native LRU later has a slightly
better original-workload mean: GPU-side retention is a relevant distinct capability.
The serialized-tool cell also retains Continuum because Stage 2 measured better
returning-request latency there despite slower batches. This capability-based
inclusion is selected before those regimes are measured. Unhinted traffic must
omit native published retention metadata as well as local wait-hint RPCs; shared
arrival-time continuation priority stays common across groups and systems.

Before Stage 4, also select three paired original real-workflow batches using the
public bounded, audit-off configuration. Keep model, byte budgets and scheduling
fixed; use the operational tier with the repository workload adapter so missing
detailed audit histories are not fabricated as causal evidence. Run disconnect,
drain and recovery after the timed workload. Preserve native activity counters,
all answers and tools, output-work/paging differences and offline verification.
This cell checks the integration profile itself rather than transferring the
research profile's performance result to an unmeasured default.

Before any additional-model measurement, also select a 1.5B Qwen cohosting cell
using the same fixed half-deployment byte budgets as Stage 3: 1,120 MiB GPU KV and
1,344 MiB CPU KV. Its 458,752-byte blocks convert GPU capacity to 2,560 blocks;
do not reuse the base model's block count as if bytes were equal. Run three paired
real-workflow repetitions and retain the original full-budget result separately,
including a legitimate all-fit/no-benefit result. This is an explicitly combined
model/memory cell, not an isolated model effect or a capacity search.
